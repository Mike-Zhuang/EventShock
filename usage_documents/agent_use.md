# Agent 使用小记：不要把 AI 困在聊天窗口里

> 这不是官方教程，也不是团队的强制规范，更不是一套唯一正确的方法，只是我在学习和做项目时积累的一些小经验。AI 工具更新很快，界面、功能和名称都可能变化，具体操作请以当前版本和官方文档为准。

本文提到的 Codex，主要指 **Codex IDE 扩展**，以及 **Codex App（即 ChatGPT 桌面 App 中的 Codex 工作区）**。我更想讨论的不是某一个按钮怎么点，而是一种更重要的使用习惯：不要只把 AI 当成聊天窗口里的问答工具，而要逐步建立 **Agent（智能代理）思维**。

## 1. 从“问一个答案”转向“交付一个结果”

聊天式 AI 很适合解释概念、提供思路、润色文字和快速问答，这些能力依然有价值。但如果任务涉及多个文件、真实环境和连续验证，只在聊天窗口中复制粘贴往往很快就会遇到限制：

- AI 看到的上下文零散，容易忽略项目中的真实约束。
- 建议和实际文件分离，复制时容易遗漏或引入新错误。
- 如果 AI 接触不到运行环境，就无法根据构建、测试或运行结果继续修正。
- 最终得到的可能只是一段“看起来合理”的答案，而不是可以使用的成果。

Agent 的区别不只是“回答得更聪明”，而是它在获得相应权限和工具后，可以围绕一个目标持续工作：读取上下文、修改文件、调用工具、观察结果、发现问题，再继续调整。

可以把两种使用方式简单理解为：

| 使用方式 | 主要目标 | 更适合的任务 |
| --- | --- | --- |
| 聊天式使用 | 获得答案、解释或建议 | 概念问答、头脑风暴、短文本润色、方案讨论 |
| Agent 式使用 | 在真实上下文中完成并验证任务 | 多文件修改、调试、文档整理、数据处理、测试与交付 |

这并不是说所有事情都应该交给 Agent。任务很小、只需要一个解释时，聊天反而更快。关键是先判断：**我现在需要的是一段回答，还是一个经过检查的结果？**

## 2. 我理解的 Agent 思维

我目前更愿意把 Agent 看成一个“能够使用工具的协作者”，而不是一个可以无条件相信的自动驾驶系统。

一个比较完整的 Agent 工作闭环通常包括：

1. **理解目标**：最终要交付什么，怎样才算完成。
2. **读取上下文**：先看现有文件、规则、依赖、日志和历史修改。
3. **制定路径**：把复杂任务拆成可以检查的小步骤。
4. **执行操作**：编辑文件、运行命令或使用已经连接的工具。
5. **验证结果**：执行测试、构建、格式检查或实际使用流程。
6. **根据反馈修正**：出现错误时读取证据、定位原因，再继续迭代。
7. **汇报和交接**：说明改了什么、如何验证、还剩什么风险。

其中最容易被忽略的是第 5 步。Agent 写出代码或文档并不等于任务完成；只有结果经过了与任务相匹配的检查，闭环才真正成立。

我自己常用一个简单公式提醒自己：

> 清晰目标 + 足够上下文 + 明确边界 + 可用工具 + 验证反馈 = 更可靠的 Agent 结果

## 3. Codex 扩展和 Codex App 怎么选择

两者都可以承载 Agent 工作方式，但适合的场景略有不同。

### Codex IDE 扩展

当任务主要围绕代码仓库展开时，我会优先使用 IDE 扩展：

- 当前正在阅读和修改代码，希望 AI 与编辑器处在同一个视图中。
- 需要结合已打开的文件、选中的代码或报错做局部修改。
- 希望一边审查差异，一边快速进行短轮次迭代。
- 需要解释陌生代码、修复单点问题或补充测试。

### Codex App（桌面端）

当任务不只是一处代码修改，或者需要管理更完整的工作过程时，我会更倾向于使用 Codex App：

- 需要同时处理代码、文档、图片、表格等不同类型的文件。
- 任务包含调查、规划、实现、复核等多个阶段。
- 希望把不同任务分开管理，或让较长的任务在独立上下文中推进。
- 在获得相应工具和权限后，需要结合浏览器、桌面应用或外部服务完成工作。

具体功能会随版本、账户和权限变化。不要因为某个入口名称改变，就把工作方式绑定死在一个界面上；真正需要保留的是“给目标、给上下文、让工具执行、用证据验收”的思路。

## 4. 开始之前，先把任务写成“可执行要求”

复杂任务并非不能交给 Agent，但目标模糊、边界缺失和验收标准不清楚，会进一步放大执行风险。

比起只说“帮我做一个系统”或“帮我优化一下”，我通常会尽量提供下面几类信息：

- **目标**：最终想解决什么问题，交付物是什么。
- **范围**：这次必须做什么，明确不做什么。
- **现状**：相关目录、已有实现、已知问题和报错信息。
- **约束**：技术栈、版本、项目规范、安全要求和禁止事项。
- **参考材料**：官方文档、设计稿、接口说明、样例或截图。
- **验收标准**：需要通过哪些测试、构建或人工检查。
- **权限边界**：哪些操作可以直接执行，哪些操作需要先确认。

设计要求也应该尽量变成可执行约束。与其只说“页面要好看”，不如在 `DESIGN.md` 或任务说明中写清字体、颜色、间距、响应式要求、参考风格和明确不要出现的设计。这样 Agent 才有可以检查的依据，而不是自由猜测审美。

例如，与其说：

> 帮我把这个项目完善一下。

不如说：

> 请先阅读 README、项目规则和相关源码。目标是完成登录失败提示，并保持现有接口不变。本次只修改前端登录流程，不调整后端和依赖。完成后运行现有测试与构建，检查错误状态和正常登录两条路径，最后汇报修改文件、验证结果和未解决风险。不要提交或推送代码。

后者并不一定更长，但目标、范围和完成标准都更清楚。

## 5. 大任务先计划，小任务也要先检查

我不再把“Plan”“Agent”当成必须固定出现的按钮名称，而把它们理解为两种工作策略：

- **先计划再执行**：适合从 0 到 1、跨模块、风险较高或需要做架构选择的任务。
- **检查后直接执行**：适合目标明确、范围较小、能够快速验证的任务。

一个任务只要会影响多个模块，我通常会先让 Agent 给出：

1. 对现状的理解。
2. 准备修改的范围。
3. 分阶段步骤与依赖关系。
4. 主要风险和不确定项。
5. 每个阶段的验收方法。

计划的价值不是让文档显得正式，而是尽早暴露理解偏差。如果方向不对，在修改几十个文件之前纠正，成本最低。

对于很小的任务，也不建议完全跳过检查。至少先让 Agent 阅读目标文件及其上下文、确认工作区状态，并寻找项目已有实现，避免凭空创造新的接口或重复功能。

## 6. 让 Agent 先读，再让它写

我自己踩过的一个坑，是太早要求 AI 输出代码。项目里往往已经存在命名规范、工具函数、接口封装和测试方式，如果 Agent 没有先读这些内容，就很容易写出“单独看没问题，放进项目就不合适”的实现。

开始工程任务前，可以明确要求它优先检查：

- `README.md` 和项目内的使用文档。
- `AGENTS.md` 或其他项目规则文件。
- 依赖清单、版本声明和配置文件。
- 与目标功能相邻的源码、测试和调用方。
- `git status` 与当前差异，避免覆盖已有修改。
- 外部接口的官方文档，而不是凭记忆猜字段。

持续有效的规则适合写入 `AGENTS.md`；只对本次任务有效的要求，直接写在当前任务中即可。这样既能减少重复说明，也不会把一次性的偏好误写成永久规则。

## 7. 用小步闭环代替“一次生成整个世界”

从 0 到 1 构建项目时，我更推荐先跑通一个最小但真实的完整链路，再逐步扩展，而不是第一轮就要求生成所有页面和所有接口。

一个比较稳妥的顺序是：

1. 明确业务目标、用户和不做的内容。
2. 确定技术约束、数据边界和验收标准。
3. 建立最小工程骨架与运行方式。
4. 先约定接口和数据契约，再完成一条端到端主路径，例如“页面提交 -> 接口处理 -> 数据保存 -> 页面反馈”。涉及前后端或外部服务时，应使用真实数据或可控测试数据验证，不用硬编码结果冒充功能完成。
5. 验证主路径后，再扩展其他模块。
6. 补充异常处理、权限、安全、日志和测试。
7. 最后完善部署、说明文档和演示流程。

每一轮都应该尽量满足三个条件：修改范围可理解、结果可以验证、失败后能够回退。这样即使 Agent 某一轮理解偏了，也不会让错误滚成一个难以收拾的大改动。

## 8. 不要只听“已经完成”，要看证据

我会要求 Agent 在交付时至少说明：

- 修改了哪些文件，以及每项修改的目的。
- 实际运行了哪些验证命令或检查流程。
- 每项验证的结果是什么。
- 哪些内容没有验证，以及原因是什么。
- 还存在什么风险或建议下一步做什么。

不同任务需要的证据也不同：

| 任务类型 | 常见验证方式 |
| --- | --- |
| 代码修改 | 现有测试、静态检查、构建、最小运行路径 |
| Bug 修复 | 先复现问题，再确认相同路径不再失败，并检查相关边界情况 |
| 配置修改 | 格式检查、工具实际读取配置、服务启动或最小健康检查 |
| Markdown 文档 | 标题层级、代码围栏、相对链接、命令完整性和术语一致性 |
| 数据或表格 | 行列数量、公式、单位、空值、异常值和关键汇总结果 |
| 前端页面 | 构建、关键交互、不同状态以及必要的视觉检查 |

验证不是对 Agent 的不信任，而是工程交付本来就需要证据。人写的内容同样需要测试和审查。

## 9. Git 是 Agent 工作时的重要保险丝

Agent 能快速修改很多文件，这既是优势，也是风险。版本管理能把“敢于尝试”和“可以恢复”同时保留下来。

我的基本习惯是：

- 开始前检查当前分支和工作区，先识别已有未提交修改。
- 在个人功能分支中工作，不直接修改或推送主分支。
- 每个可运行、可验证的里程碑形成一个清晰检查点。
- 提交前审查差异，不把无关文件混进当前任务。
- 不让 Agent 擅自提交、推送、合并或创建 Pull Request。
- 出现问题时先理解差异，不使用可能删除现有修改的破坏性命令。

本项目的具体协作方式见 [Git 使用指南](git_use.md)。

## 10. 权限越大，边界越要清楚

Agent 可以使用工具，不代表它应该默认拥有所有权限。尤其是下面这些操作，我会保持更谨慎的确认和复核：

- 删除文件、覆盖大量已有内容或执行不可逆命令。
- 安装依赖、修改系统配置或更换全局软件源。
- 提交、推送、合并代码或修改远程仓库状态。
- 发送邮件、发布内容、部署上线或操作真实业务数据。
- 读取、复制或输出密钥、令牌、隐私数据和内部地址。

比较稳妥的原则是：**读取和分析可以更主动，产生外部影响的操作要更克制；权限按任务最小化，结果由人最终负责。**

## 11. 几个常见误区

### 误区一：提示词越长越好

提示词的价值不在字数，而在信息是否有效。与其堆很多形容词，不如写清目标、范围、约束和验收标准。

### 误区二：AI 出错后立刻人工接管

如果错误信息和环境都在 Agent 的权限范围内，可以先让它读取完整报错、检查相关代码、提出假设并验证。涉及业务决定、账号权限、不可逆操作或外部影响时，再由人补充信息或作出确认。

### 误区三：把 Agent 当成替自己负责的人

Agent 可以承担大量执行工作，但目标选择、权限授予、关键取舍和最终验收仍然属于人。把责任一起外包，往往才是最大的风险。

## 12. 一个可以直接复用的任务模板

下面是我目前比较常用的写法，可以按任务大小删减：

```text
请作为这个项目的执行 Agent，先理解现状，再完成任务。

目标：
- [最终要交付的结果]

范围：
- 必须完成：[内容]
- 不在本次范围：[内容]

开始前：
1. 阅读 README.md、AGENTS.md 和相关文档。
2. 检查 git status，保留已有修改。
3. 查找现有实现、接口、配置和测试，不要凭猜测创造新接口。

约束：
- [技术、版本、设计、安全或课程要求]
- 未经确认，不要提交、推送、部署或执行不可逆操作。

验收标准：
1. [可以客观检查的结果一]
2. [可以客观检查的结果二]
3. 运行项目已有的相关测试或检查。

执行方式：
- 如果任务跨多个模块，先给出简短计划和风险；范围明确的小任务可以直接执行。
- 修改保持增量，不删除无关功能。
- 遇到错误时先读取证据并排查，不要未经验证就归因于环境。

完成后请汇报：
1. 修改内容与文件清单。
2. 实际执行的验证及结果。
3. 未验证内容、剩余风险和后续建议。
```

模板不是为了让每次任务都变得很正式，而是帮助自己不忘记最关键的信息。熟悉以后，可以只保留真正与当前任务有关的部分。

## 13. 最后给自己的五句提醒

1. **不要只问 AI “怎么做”，也可以让它在真实上下文中做完并验证。**
2. **先给结果定义，再给执行自由；先说明边界，再授予工具权限。**
3. **让 Agent 先读项目和官方文档，不要鼓励它猜接口、猜业务。**
4. **一次只推进一个可以验证的里程碑，稳定后再扩展。**
5. **版本管理、最小权限和人工复核，是使用 Agent 时最基本的安全网。**

## 结语

我认为，AI 使用能力的分水岭不只是“会不会写提示词”，而是能不能把一个模糊愿望整理成目标明确、边界清楚、可以执行和验证的任务。

不要把 AI 困在聊天窗口里，也不要把 Agent 神化成全自动替代者。更合适的关系是：人负责方向、约束和验收，Agent 负责在允许的范围内读取上下文、使用工具、推进执行并根据证据迭代。这样，AI 才能从“会回答问题”逐渐变成“能够一起完成工作”的协作者。
